# CAP-теорема: Анализ для поисковой системы

## Введение в CAP-теорему

CAP-теорема (теорема Брюера) утверждает, что распределённая система не может одновременно гарантировать все три свойства:

- **C (Consistency)** — Консистентность: все узлы видят одинаковые данные в один момент времени
- **A (Availability)** — Доступность: система всегда отвечает на запросы (успешно или с ошибкой)
- **P (Partition Tolerance)** — Устойчивость к разделению: система продолжает работать при потере связи между узлами

В реальных распределённых системах разделение сети (P) неизбежно, поэтому выбор всегда между **CP** (консистентность + устойчивость) и **AP** (доступность + устойчивость).

## Выбор компромисса для поисковой системы: **AP**

### Обоснование

Для поисковой системы (вариант 8) мы выбираем **AP** (Availability + Partition Tolerance):

**Причины:**

1. **Критичность доступности поиска**
   - Пользователи ожидают, что поиск всегда работает
   - Лучше показать немного устаревшие результаты, чем вообще не отвечать
   - Простои поиска = потеря пользователей

2. **Eventual Consistency приемлема**
   - Новые документы могут индексироваться с задержкой 5-10 секунд
   - Пользователь поймёт, что его только что загруженный документ появится в поиске через несколько секунд
   - Это типичное поведение для большинства поисковых систем (Google, Elasticsearch)

3. **Geo-distributed deployment**
   - Датацентры в разных регионах (EU, US)
   - Network partition между регионами возможен
   - Каждый регион должен работать автономно

4. **Асинхронная индексация**
   - Индексация через очередь RabbitMQ уже подразумевает eventual consistency
   - Документ сначала сохраняется, потом индексируется воркером

### Исключения (CP для критичных операций)

Некоторые операции требуют строгой консистентности:

- **User authentication**: Логин/регистрация должны быть консистентными (запись в Primary)
- **Document deletion**: Удаление должно быть синхронным (иначе пользователь увидит удалённый документ в поиске)
- **User quota checks**: Лимиты запросов должны быть точными

Для этих операций мы используем **синхронную запись в PostgreSQL Primary** с подтверждением.

## Сценарии сбоев и поведение системы

### Таблица компромиссов

| Сценарий сбоя | Поведение системы | C | A | P | Компромисс |
|---------------|-------------------|---|---|---|------------|
| **Primary DB недоступна** | Поиск работает с Standby (read-only), создание документов откладывается в очередь | ⚠️ | ✅ | ✅ | A сохраняется, C временно нарушается |
| **Standby DB недоступна** | Поиск переключается на Primary, производительность снижается | ✅ | ✅ | ✅ | Полная работоспособность |
| **Network partition EU-US** | Каждый регион работает независимо, синхронизация после восстановления | ⚠️ | ✅ | ✅ | AP, eventual consistency |
| **Задержка репликации (10 сек)** | Пользователь не видит свой документ в поиске сразу | ⚠️ | ✅ | ✅ | Eventual consistency (acceptable) |
| **Indexer Worker перегружен** | Документы накапливаются в очереди, индексация отложена | ⚠️ | ✅ | ✅ | A сохраняется, C ослабляется |
| **ValKey (cache) недоступен** | Все запросы идут в БД, latency увеличивается, но система работает | ✅ | ✅ | ✅ | Performance degradation |
| **RabbitMQ недоступен** | Документы создаются, но не индексируются (очередь в памяти) | ⚠️ | ✅ | ✅ | Indexing paused |
| **Nginx недоступен** | Полный отказ (single point of failure) | ❌ | ❌ | ❌ | Critical failure |

**Обозначения:**
- ✅ Гарантируется
- ⚠️ Ослаблено (eventual consistency)
- ❌ Нарушено

### Детальный анализ сценариев

#### 1. Primary Database Failure

**Что происходит:**
```
Primary DB (write) ━━✗━━━━
                         ↓
Standby DB (read)   ━━━━━✓━━ (promoted to Primary)
```

**CAP анализ:**
- **C (Consistency)**: ⚠️ Нарушается временно (до 30 сек failover)
- **A (Availability)**: ✅ Поиск продолжает работать с Standby
- **P (Partition Tolerance)**: ✅ Система устойчива к отказу узла

**Поведение:**
1. pg_auto_failover детектирует сбой Primary (30 сек)
2. Standby автоматически промотится в Primary
3. Поиск продолжает работать (читал из Standby)
4. Создание документов откладывается в RabbitMQ или возвращает 503

**Приемлемость:** ✅ Да, потому что:
- Поиск (основная функция) работает без перерыва
- 30 сек downtime для записи — приемлемо для некритичной системы
- Пользователи увидят "Service temporarily unavailable" для загрузки документов

#### 2. Network Partition между датацентрами

**Что происходит:**
```
EU Datacenter          US Datacenter
    ↓                       ↓
[Nginx EU]  ━━✗━━━━━━━━ [Nginx US]
    ↓                       ↓
[Services]              [Services]
    ↓                       ↓
[Local DB]              [Local DB]
```

**CAP анализ:**
- **C (Consistency)**: ⚠️ Eventual consistency между регионами
- **A (Availability)**: ✅ Оба региона работают независимо
- **P (Partition Tolerance)**: ✅ Система устойчива к разделению

**Поведение:**
1. DNS направляет пользователей в ближайший датацентр
2. Каждый датацентр работает автономно
3. После восстановления связи — синхронизация через event log (Audit Service)

**Приемлемость:** ✅ Да, потому что:
- Пользователи не замечают проблемы
- Данные синхронизируются асинхронно
- Конфликты разрешаются через "last-write-wins" или версионирование

#### 3. Replication Lag (задержка репликации)

**Что происходит:**
```
User uploads document → Primary DB (write) ━━━━━━➤ Standby DB (read, +10 sec)
                            ↓ (immediate)                ↓ (delayed)
                        Document saved              Search doesn't see it yet
```

**CAP анализ:**
- **C (Consistency)**: ⚠️ Read-after-write inconsistency
- **A (Availability)**: ✅ Обе операции успешны
- **P (Partition Tolerance)**: ✅ N/A (нет partition)

**Поведение:**
1. Пользователь загружает документ → сохранён в Primary
2. Пользователь ищет свой документ → Search читает из Standby (ещё не реплицировано)
3. Через 10 секунд документ появляется в поиске

**Приемлемость:** ✅ Да, потому что:
- Это стандартное поведение для eventual consistency
- UI может показать "Документ загружен, будет доступен в поиске через несколько секунд"
- Альтернатива: Search может временно читать из Primary для недавно загруженных документов (sticky read)

#### 4. Cache Unavailable

**Что происходит:**
```
Search query → ValKey ━━✗━━
                  ↓
            Cache MISS (always)
                  ↓
         Database (slow, but works)
```

**CAP анализ:**
- **C (Consistency)**: ✅ Всегда актуальные данные (bypass cache)
- **A (Availability)**: ✅ Поиск работает, но медленнее
- **P (Partition Tolerance)**: ✅ Система деградирует gracefully

**Поведение:**
1. Все поисковые запросы идут напрямую в PostgreSQL
2. Latency увеличивается: 50ms → 200ms
3. Нагрузка на БД растёт, может потребоваться rate limiting

**Приемлемость:** ✅ Да, потому что:
- Функциональность сохраняется полностью
- Performance degradation — временная проблема
- Пользователи получают корректные результаты

## Стратегии для усиления консистентности (при необходимости)

Если потребуется усилить консистентность (сдвиг к CP):

### 1. Synchronous Replication

```yaml
# PostgreSQL config
synchronous_commit = on
synchronous_standby_names = 'postgres-standby'
```

**Плюсы:**
- Primary ждёт подтверждения от Standby → read-after-write consistency
- Нет replication lag

**Минусы:**
- Latency увеличивается на 10-50ms (network roundtrip)
- При недоступности Standby — Primary блокируется (нарушается A)

### 2. Sticky Sessions для read-after-write

```python
# Временно читать из Primary после записи
if request.headers.get('X-Recent-Write'):
    db = primary_connection
else:
    db = standby_connection
```

**Плюсы:**
- Пользователь всегда видит свои изменения
- Standby используется для остальных запросов

**Минусы:**
- Усложнение логики
- Нагрузка на Primary растёт

### 3. Version Vectors для conflict resolution

```python
# Event Sourcing помогает разрешить конфликты
def merge_conflicting_events(events_eu, events_us):
    # Векторные часы для определения порядка
    return sorted_by_lamport_timestamp(events_eu + events_us)
```

## Мониторинг CAP-метрик

### Метрики для отслеживания компромиссов

1. **Consistency Lag**
   ```promql
   # Задержка репликации
   pg_replication_lag_seconds
   ```
   Порог: < 5 секунд

2. **Availability**
   ```promql
   # Uptime всех сервисов
   up{job="search-service"} == 1
   ```
   Цель: 99.9% (8.76 часов downtime в год)

3. **Read-after-write Success Rate**
   ```promql
   # % пользователей, увидевших свои изменения сразу
   rate(read_after_write_success_total[5m])
   ```
   Цель: > 95%

4. **Conflict Resolution Rate**
   ```promql
   # Количество конфликтов при синхронизации
   rate(sync_conflicts_total[5m])
   ```
   Ожидаемо: < 0.01% запросов

## Заключение

**Итоговый компромисс для поисковой системы:**

```
          Consistency
               ↑
               |
       [Auth/Delete]  ← CP для критичных операций
               |
               |──────────── Компромисс
               |
        [Search/Index]  ← AP для основного функционала
               |
               ↓
          Availability
```

**Ключевые решения:**

1. ✅ **AP для поиска**: Eventual consistency + высокая доступность
2. ✅ **CP для аутентификации**: Строгая консистентность для безопасности
3. ✅ **Graceful degradation**: При сбоях система продолжает работать с ограничениями
4. ✅ **Мониторинг lag**: Отслеживание задержек репликации и инвалидация кэша
5. ✅ **Event Sourcing**: Позволяет восстановить консистентность post-factum

**Почему это оптимально:**

- Поисковые системы — tolerance-критичные приложения (доступность важнее моментальной консистентности)
- Пользователи предпочитают быстрый поиск с небольшой задержкой индексации, чем медленный/недоступный поиск
- Event Sourcing даёт возможность аудита и восстановления даже при eventual consistency
- Асинхронная индексация naturally подразумевает eventual consistency

**Риски и митигация:**

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Пользователь не видит свой документ | Средняя | UI notification + sticky reads |
| Конфликты при синхронизации | Низкая | Event Sourcing + version vectors |
| Длительный replication lag | Низкая | Мониторинг + алерты + автоматический failback |

Этот CAP-компромисс обеспечивает **оптимальный баланс между производительностью, доступностью и консистентностью** для поисковой системы с высокой нагрузкой.
